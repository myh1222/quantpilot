# ADR-0001: GATE-TV-01 TradingView feasibility result

- Status: **FAIL / ENTITLEMENT BLOCKED**
- Date: 2026-09-11
- Account plan observed: TradingView Basic
- Chart layout: `AKITEcJL`
- Probe: `QuantPilot Watchlist Alert Spike`
- Run ID: `P0-20260911-01`

## Decision

Do not start the TradingView-dependent Phase 1 with the tested account.

The preferred Watchlist Alert architecture cannot be exercised on Basic, and the
per-symbol fallback is also unavailable because the account reports zero technical
alerts and does not allow webhook notifications. Starting a trial or changing a
paid subscription is an account-owner decision and was not performed by the spike.

After an entitlement upgrade:

1. Rerun Watchlist Alert first.
2. If it correctly executes the custom Pine script per member, implement only
   watchlist mode.
3. If Watchlist Alert is unavailable or fails per-member dynamic evaluation while
   ordinary technical alerts and webhooks work, implement only per-symbol
   aggregated `alert()` mode.
4. Do not implement both control paths speculatively.

## Observed evidence

### Pine and alert configuration

- The probe compiled, was saved, and was mounted on `HKEX:981` and
  `BINANCE:BTCUSDT`.
- The indicator produced a live `Probe EMA` value on both symbols.
- The ordinary alert dialog selected the probe and exposed
  `Any alert() function call`.
- Probe inputs were visible as `gate-tv-01-v1`, `P0-20260911-01`, config version
  `1`, and EMA length `20`.
- On `BINANCE:BTCUSDT`, the market was open and the alert dialog accepted the
  chart interval (`15 minutes`, later reduced to `1 minute` for a fast probe).

This proves that the Pine script is syntactically valid and is eligible as an
ordinary `alert()` source. It does **not** prove server-side execution, dynamic
message evaluation, or Watchlist Alert compatibility because no technical alert
could be saved.

### Subscription blockers

TradingView displayed all three blockers in the logged-in UI:

1. Watchlist Alert: “One alert to track an entire watchlist” followed by an upgrade
   prompt stating that Watchlist Alerts require Premium or higher.
2. Webhook notification: “React instantly with webhook notifications” followed by
   an upgraded-plan prompt; the Webhook URL input remained disabled.
3. Ordinary technical alert: saving failed and the upgrade prompt stated,
   “Right now, you have a limit of 0 technical alerts in your plan.”

Therefore neither the preferred mode nor the per-symbol fallback is executable
with the tested entitlement.

### Market-data entitlement

`HKEX:981` was labeled `HKEX_DLY:981`, and TradingView displayed
`Quotes are delayed by 15 min`. This account must not be described or operated as
realtime for the HKEX market until the exchange data entitlement is upgraded and
reverified. `BINANCE:BTCUSDT` displayed `Market open` and was suitable only as a
24x7 functional probe.

### Independently verified receiver components

- Local `/health`: PASS.
- Authenticated webhook validation: PASS.
- Atomic SQLite signal plus durable job write: PASS.
- Delivery idempotency: PASS.
- Worker lease and job completion: PASS.
- Secret redaction from process output: PASS.
- Public HTTPS reachability: PASS using ephemeral tunnels.
- Public POST acceptance and duplicate absorption: PASS using an ephemeral
  localhost.run endpoint.

These are component results, not a substitute for a TradingView-originated POST.

## Exact rerun checklist

Prerequisites:

- A TradingView plan with at least one technical alert and webhook notifications.
- 2FA enabled for the account.
- For the preferred branch, Watchlist Alert entitlement.
- Realtime data entitlement for each intended exchange.
- A controlled public HTTPS endpoint; do not rely on the ephemeral spike URL.

Rerun:

1. Start the gateway and verify `/health` locally and publicly.
2. Use a fresh high-entropy webhook path secret.
3. Mount the saved probe with a fresh `run_id` and enable
   `TEST ONLY: emit every confirmed bar`.
4. Create the Watchlist Alert with `Any alert() function call` and the webhook URL.
5. Use at least two 24x7 symbols and one exceptional member (invalid, stopped, or
   unavailable) while staying below TradingView fire-control limits.
6. Verify that received JSON has the actual member's `symbol`, `ticker`, `event`,
   and canonical `timeframe`, and that `bar_open_time_ms` matches the bar.
7. Repeat one delivery and verify a single logical signal/job is retained.
8. Add and remove a Watchlist member and verify automatic coverage changes.
9. Record alert expiration and verify the reconciler's renewal input.
10. Disable the test alert immediately after evidence collection.

Only after all runtime checks succeed may this ADR be superseded with a PASS ADR.
